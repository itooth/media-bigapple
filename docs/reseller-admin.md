# 代理商配置与运行维护

## 使用流程

原站页脚齿轮 → 管理员密码 → 配置表 → 新增一行 → 上传 Logo、填写网站名称 → 取消不展示的活动 → 保存 → 复制链接。

新建行默认选择当前全部活动。活动选择按唯一文件夹标识保存，避免同一个 manifest id 的副本相互覆盖。既有旧活动链接仍可打开，新的站内活动链接使用唯一标识。分类、搜索、详情和两种相册始终保留代理商编号前缀。

每行保存独立生效；收起多选框不会保存。未保存离开会提醒；请求失败会保留填写内容。会话过期后可重新登录，仍保留当前编辑。重复的新增请求不会创建第二家代理商，多窗口同时修改同一条配置时会提示版本冲突。

活动库后续新增项目后，新代理商默认包含这些项目；已有代理商仍保持上次保存的选择，可在管理表中勾选新项目。删除素材库活动不会让其他活动自动顶替它。

## 部署

### 已准备的首次上线数据

| 编号 | 网站 | 初次展示范围 |
| --- | --- | --- |
| 6024 | Polo Events | 本地已有配置的 29 场 |
| 6025 | 有推传媒 · 活动案例 | 旧版 33 场，按活动文件夹唯一标识匹配 |
| 6026 | WinFlow · 用户案例 | 当前全部 34 场 |

有推与原站的 1 场差异是 `2026-6-12_周周K12专场_副本`；保留旧版范围，不靠重名标题匹配。WinFlow 字样暂不清理，各品牌共用原活动文案与原标签。前台统一移除未开发的 Partners / About / Newsroom。

`bootstrap/resellers.json` 是本次首次上线快照，三个小型 PNG 在 `bootstrap/logos/`，均不含密码。有推 Logo 仅按旧版横向显示窗口裁去上下空白；WinFlow 等比缩小作为上传版本，原始素材不修改。

首次启动按以下顺序运行，完成后才监听端口：

1. 校验管理员配置，生产环境必须有 `BIGAPPLE_DATA_DIR`；创建／升级 SQLite 表。
2. 检查未执行的品牌导入，验证编号、活动和 Logo，上传至对象存储。请求重试使用内容哈希地址。
3. 事务同步发布包的活动目录到数据库。活动从新版目录移除后归档而不删除其存档。
4. 在一个事务中写入新品牌与导入记录。如果本地已有相同编号、相同创建标识，仅记录已导入，保留手动修改；其他编号冲突直接报错，避免覆盖。

后续部署看到导入记录就跳过品牌初始化，名称、Logo 和勾选结果不会还原。本地新增或修改配置不会通过 Git 自动同步生产；首次快照之后，以正式服务器后台的修改为准。若首次上线前要携带新的本地更改，须重新核对首次快照。

这次增加了登录、持久化配置和上传，必须使用 Docker 模式，不能只上传 `dist/index.html`。Dockerfile 在构建阶段安装前端依赖并生成文件，运行阶段仅使用 Node.js 内置模块，无需本机安装 Docker。

环境变量：

| 名称 | 作用 |
| --- | --- |
| `ADMIN_PASSWORD` | 至少 12 位的管理员密码，使用平台 Secrets 设置，必填 |
| `PORT` | HTTP 端口，默认 3000；平台会注入 |
| `BIGAPPLE_DATA_DIR` | 生产环境必填，平台注入的持久化目录 `/data`；本地默认 `.data/` |
| `APP_ORIGIN` | 可选的完整公开来源，例如 `https://media.bigapple.work`，不得带路径或结尾斜杠；用于请求来源校验 |
| `BIGAPPLE_STORAGE_URL`、`BIGAPPLE_STORAGE_TOKEN` | 平台对象存储接口及服务端凭据，Logo 上传使用；不能传给浏览器 |
| `NODE_ENV` | Docker 运行时设为 `production`，启用 Secure 管理员 Cookie |

上线前先核对已有应用及授权，将密码配置为 Secret，使用原应用的 Docker 更新流程；保留原 appId、地址和持久化卷。此代码提交不等于已部署。无需重建应用、移动原照片或更换图床。

启动后 `/api/health` 为健康检查。就绪检查之后还应验证原站、登录、Logo 上传、保存和代理商深链接。开发过程中不能将真实管理员密码放进 `VITE_*`、Git、截图或客户端构建产物。

### 合并 main 后的发布步骤

`.github/workflows/check.yml` 仅执行测试和构建，不含部署凭据，也不自动发布。合并后：

1. 用指定 bigapple-deploy Skill 查询应用注册表，确认原站对应的 appId 与地址。先检查旧应用运行模式和已有 Secrets 名称，保留已有手填配置。
2. 为原应用设置 `ADMIN_PASSWORD` Secret；不能复用仓库示例值。确认平台注入 `/data` 与对象存储凭据。缺少对象存储时首次导入会明确失败。
3. 先执行 `npm run release:prepare`，只把命令返回的干净目录交给部署 Skill。Skill 的 ZIP 脚本不会读取 `.gitignore` / `.dockerignore`，不要直接传开发工作目录。按 Docker 模式 `--inspect` 检查干净目录后，再部署同一个应用。首次从静态切换为后端服务，保留原 appId 与主站地址。
4. 验证 `/api/health`、原站、管理员登录、三个品牌的 Logo／数量、相册与深链接；保存一项设置后验证重启仍保留。
5. 独立旧站 `polo-events` 和 `youtui-events` 继续保留；本次代码不会更新它们，也不自动重定向。新地址是原站域名加 `/6024`、`/6025`、`/6026`。

发布更新前做一致性备份。如果应用发布失败，保留上一版及持久化卷。活动内容回滚可以重新同步上一版目录；数据库修改不能靠回滚代码撤销，须按下面的恢复步骤操作。

## 数据与备份

- `resellers.sqlite` 位于持久化目录，保存活动目录、编号、品牌设置、所选活动唯一标识、版本号和导入记录。更新应用不应删除这个目录。
- Logo 在浏览器内转成最长边不超过 1024 像素的 PNG，服务端限制为 2 MB。生产环境存对象存储，并按内容哈希去重；本地开发可放 `.data/logos/`。原 SVG 文件仅在本机读取，不作为可执行 SVG 上传。
- 开发密码文件、数据库、上传 Logo 和 `.env` 已从 Git 与 Docker 构建上下文排除。
- 备份应使用 SQLite 一致性备份工具，或停服后复制整个持久化目录；运行中不要仅复制 WAL 模式的单个数据库文件。对象存储 Logo 也应保留，数据库只保存其引用。
- 不提供删除接口，避免误删配置或正在使用的 Logo。
- 修改管理员密码并重启服务会使现有会话失效。会话默认 8 小时，密码错误尝试有速率限制。

在线备份：开发环境运行 `npm run db:backup`，容器内运行 `node scripts/backup-data.mjs`。可用命令的最后一个参数指定新目录。使用 Node SQLite backup API 创建包含 WAL 中已提交内容的一致性快照，默认存到持久化目录的 `backups/时间/`；附带本地 Logo 和外部 Logo 引用清单，不含密码。已有目标目录不会被覆盖。

备份副本应另行保存到服务器之外；同一持久化卷里的备份不能防止整卷丢失。目前不自动安排定时备份。生产对象存储中的 Logo 和原图床内容需继续保留，数据库备份不包含这些外部文件。

恢复前停止服务并另存当前数据目录，将备份中的 `resellers.sqlite` 和（如有）`logos/` 放到一个干净的持久化目录，再使用匹配版本的程序启动。不能将备份数据库与原有 `-wal` / `-shm` 混用。确认品牌配置、图片引用与活动计数后再恢复访问。

## 案例来源可复现

原版构建依赖电脑外部的素材库。`siteContent.snapshot.json` 从仓库基线 `a12a7d3` 已发布 HTML 的字面量数据迁移，包含活动 manifest、标签、作品与报道链接；迁移器只解析 AST 字面量，不执行 HTML。

当外部素材库存在时，Vite 继续读取素材库并刷新快照；不存在时使用快照。构建先生成服务端活动目录，再生成不含全量活动数据的前端脚本。代理商 API 只返回该代理商所选活动，原站 API 则提供公开完整目录。

`scripts/extract-published-snapshot.mjs` 是一次性迁移脚本，针对旧版产物变量名，不能用于新版 `dist/index.html`。日常维护按原素材库流程更新，不重新运行迁移器。

## 回归检查

`npm test` 覆盖原选图规则、日期分组、代理商路由、认证、跨站请求拒绝、整场活动排除、重启持久化、防重复创建、并发编辑冲突、Logo 上传及登录限速。
同时覆盖首次导入、已有数据升级、编号冲突、发布目录更新／回滚、上传失败后重试不产生半成品，以及在线备份恢复。

浏览器还应检查：新行 34/34 默认勾选、取消一项后 33/34、上传真实 Logo、保存刷新、复制链接、代理商搜索和分类计数、排除活动的深链接、相册返回，以及手机端表格和多选框。
