# 媒体字段合同

前端不存放任何图片文件。每张图片在云端有一个公开链接，前端只保存字段。

## 字段（13 项）

| 序号 | 字段 | 含义 | 取值 | 来源 |
|---:|---|---|---|---|
| 1 | `activityId` | 所属活动编号 | 如 `01-1` | 目录派生 |
| 2 | `path` | 相对路径 | 从 `01_活动照片/` 起，不带活动名前缀 | 目录派生 |
| 3 | `name` | 文件名 | 原文件名，一字不改 | 目录派生 |
| 4 | `category` | 粗分类 | `活动` / `案例` / `社交媒体` | 顶层目录派生 |
| 5 | `categoryText` | 细分类文本 | 见下方词表 | 由 `name` 中间段解析 |
| 6 | `rating` | 评分，同时是排序键 | 五位数字 | 由 `name` 第一段解析 |
| 7 | `description` | 图片描述 | 一句人话 | 由 `name` 尾段解析，可人工改写 |
| 8 | `isCover` | 是否该活动封面 | `1` / `0` | 由 `name` 中「封面」标记解析 |
| 9 | `onHomePage` | 是否进活动页第一屏「活动剪影」 | `1` / `0` | 由 `name` 中「首页」标记解析 |
| 10 | `url` | 云链接 | `https://media.bigapple.app/...` | 上传后回填 |
| 11 | `hash` | 云端文件哈希 | 64 位十六进制 | 上传后回填 |
| 12 | `originBytes` | 原图体积 | 字节 | 扫描时读取 |
| 13 | `cloudBytes` | 云端体积 | 字节 | 上传后回填 |

## 细分类词表（三类互不共用）

- 活动：海报 / 大合照 / 人物 / 演讲 / 演示 / 互动 / 现场信息
- 案例：作品界面 / 作品演示 / 主图 / 辅图 / 封面
- 社交媒体（press）：报道截图 / 媒体版面 / 公众号截图 / 视频号封面

## 名字解析规则

文件名格式：`五位数字分数_内容分类_具体描述.扩展名`，段数不固定。

1. 第一段是五位数字 → `rating`
2. 出现「首页」段 → `onHomePage = 1`
3. 出现「封面」段 → `isCover = 1`
4. 其余中间段 → `categoryText`
5. 尾段 → `description`
6. 解析不出来的文件必须报错，不允许猜测

## 三条硬规则

1. `hash` 必须能在 `url` 里找到，对不上就不允许上线
2. 每个活动 `isCover = 1` 的记录最多一条，超过则报错
3. 没有 `url` 的记录不进任何列表，不渲染（图片、视频一视同仁：宁可少一个格子，也不留空白框/空播放器）

## 取值规范

- `isCover`、`onHomePage` 只写 `1` 或 `0`
- 不写 `null`、不写空字符串、不写字符串 `"1"`
- `rating` 不足五位补 0
- `category` 只能是三个值之一

## 职责边界

- `素材库`：原图真源，位于项目之外，只增不改
- 索引文件：回答「有哪些图」，纯文本，不含图片
- 云端：回答「图在哪」，只存可公开访问的版本
- 前端：回答「怎么显示」，只有代码和索引

## 索引怎么来

```bash
node scripts/build-media-index.mjs
```

| 方向 | 文件 | 说明 |
|---|---|---|
| 输入 | `anli_web_图片存档/网站压缩素材/` | **候选集合的来源**：现场扫描，就是线上原本展示的那批图（在前端项目之外，可用 `ANLI_WEBSITE_MEDIA` 覆盖） |
| 输入 | `../../素材库/<活动>/manifest.json` | 活动 id / 标题 / 日期 / 地点 |
| 输入 | `../../素材库/` | 原图，用来补 `originBytes` |
| 输入 | `src/data/publicMediaMap.generated.js` | 云端清单（hash → url） |
| 输出 | `src/data/mediaIndex.generated.js` | 前端唯一的媒体索引 |
| 输出 | `docs/media-index-report.md` | 体检报告 |

生成器只读，不修改、不删除任何图片。

## 两条对应规则

1. **候选集合**取「网站压缩素材」的现场扫描结果，也就是改造前线上展示的那批图。
   云端有、本地没有的不补；本地有、云端没有的记为 `url` 空，前端不渲染。
2. **云端对应**按文件 `sha256` 精确比对云端清单里的 `hash`。
   上传上去的云端文件就是「网站压缩素材」里那份文件本身，字节完全一致，
   所以即使文件后来改过名字（例如 `10050_封面_大合照_…jpg` 在云端仍叫
   `09900_首页_大合照_…jpg`），也能一对一对上，不需要猜、不会配错图。
   兜底再按「同一活动 + 主干名相同」匹配一次，覆盖压缩时改过扩展名的情况。

实测：3748 条候选里 3192 条对应上云端（sha256 3135 + 主干名 57），
556 条对应不上（视频、以及案例里的源码/构建产物）。

## `path` / `name` 取哪一份

`path` / `name` 取「网站压缩素材」那一份，因为云端和展示用的就是它。
`originBytes` 取「素材库」原图的文件大小，按主干名配对，配不上记 0。

## 「封面」标记只对活动生效

- 活动图里的 `封面` → `isCover = 1`（活动封面）
- 案例图里的 `封面` → 只是案例自己的封面，算 `categoryText`，`isCover` 仍是 0

封面 = 评分最高的、带「封面」标记的那张；没有标记就退回评分最高的一张。
**没有 `封面` 标记的活动不会自动拿别的图顶上。**

## 视频也在索引里

`videos` 和图片共用这 13 个字段，用 `name` 的扩展名区分（`.mp4` / `.mov`）。
选图时按扩展名过滤，不要把视频选进图片列表。

## 上传与额度（2026-09-16 补充）

新图/修复图的上传脚本：`scripts/upload-media.mjs`（旧的 `upload-public-media-map.mjs`
用 Windows 路径和旧接口，已不能工作，保留仅作参考）。

```bash
node scripts/upload-media.mjs \
  --media-root "/Users/Admin/Desktop/anli_web_图片存档/网站压缩素材" \
  --folders "2026-09-05-光耀基金会活动" [--dry-run]
```

- 接口：`PUT https://api.bigapple.work/api/apps/<appId>/public-objects/media/<sha256>/<sha256>.<ext>`
  （**必须用 appId**，用 slug 会返回 `Application not found`；skill 版本需 ≥ 2.4.0）
- 凭据：`~/.bigapple/deployment-credential.json` + `~/.bigapple/publisher.json`
- **额度三层（以 `bigapple-deploy` Skill 的 `## Resource limits` 为准，2026-09-16 实测核对）**：

  | 层级 | 上限 | 撞到时的返回 |
  |---|---|---|
  | 单个对象（R2 object） | 128 MB | `413 {"error":"对象超过 128MB 限制"}` |
  | 单个应用（one app） | 128 MB | `413 {"error":"应用存储额度不足：当前 51193KB，请求 100MB，上限 128MB"}` |
  | **一个 publisher 跨应用合计** | **256 MB** | 同上（换应用也一样） |

  所以一个账号最多 2 个满额应用。**用完一个应用的 128 MB 时，开第二个应用即可再拿 128 MB**
  （见下方「应用分仓」）。Skill 里另外几条部署限制也一并记着：
  静态包 200 MB、Docker 包 200 MB 以内 / Docker 100 MB、解包后 256 MB 且不超过 20000 个文件。

- 平台自己的媒体库应用（`pub_e06ae57c-…/apps/media`，现有 3000+ 张图所在）
  不归本机凭据所属账号，既读不到清单也写不进去 —— 大批量上传前先 `--dry-run` 看体积。
- 补齐「本地有、云端没有」的图，用 `scripts/upload-missing-media.mjs`：

```bash
node scripts/upload-missing-media.mjs --dry-run   # 列出要补的图、按活动的体积
node scripts/upload-missing-media.mjs             # 真正上传（图片，不含视频）
node scripts/upload-missing-media.mjs --include-videos
node scripts/upload-missing-media.mjs --max-bytes 52428800   # 只传前 50 MB
node scripts/upload-missing-media.mjs --app bigapple-events-media   # 传到第二个应用
```

  脚本幂等：sha256 相同就跳过；额度不足会自动停下并保留已传部分，扩额度后重跑即续传。

### 占位白图（1×1）处理规则

压缩环节会产出 **631 字节的 1×1 白图**（文件名正常、能打开、肉眼是纯白），
一旦它拿到云端链接，页面上就会出现一个个白方块 —— 旧版 9/9 构建的 `09-05-guangyao`
（16 张）和 `05-06-3`（26 张）就是这个毛病。

规则：

1. 上传前一律拦掉。`scripts/upload-missing-media.mjs` 用 `scripts/lib/imageDimensions.mjs`
   只读文件头取像素尺寸，任一边 ≤ 2 像素就跳过（不会误伤正常小图标，因为它读的是真实像素）。
2. 已经传上去的，用 `scripts/purge-placeholder-media.mjs` 清理：

```bash
node scripts/purge-placeholder-media.mjs --dry-run   # 先看要删什么
node scripts/purge-placeholder-media.mjs             # 删云端对象 + 从清单摘除
node scripts/build-media-index.mjs && npm run build
```

3. 摘除后索引里 `url` 为空 → 页面不渲染 → 不会留白框。

### 修掉的一个真问题：视频扩展名不匹配

页面上的视频清单来自旧数据 `libraryEvents.generated.js`，里面写的是 `.mov`，
而云端/索引里存的是 `.mp4`。`events.js` 取视频时**没做扩展名归一化**，
导致 **92 个视频明明有云端链接、却查不到、页面白丢**（例：`07-bnijeff-13` 相册 0 个视频）。

修法（`src/data/events.js`，和图片走同一条归一化函数）：

```js
// 改前：mediaUrl(record.id, asset.path)
// 改后：
.map((asset, index) => ({ id: `${record.id}-video-${index}`, src: mediaUrl(record.id, websiteAssetPath(asset.path)), title: captionOf(asset.name) }))
```

修完实测：`07-bnijeff-13` 0 → 5 个、`05-06-3` → 7 个、`activity-28` → 7 个、`07-11-9` → 13 个。

### 并行上传（快 2 倍）

`upload-missing-media.mjs` 加了 `--concurrency N` 和自动重试。实测：

| 并发数 | 实测吞吐 |
|---|---|
| 1（串行） | 0.36 MB/s |
| 5–6 | **0.7 MB/s（最快）** |
| 15 | 0.27 MB/s（开始被网关拒绝） |
| 20 | 大面积 `fetch failed`，全失败 |

**结论：并发 5–6 是最优点，不要盲目拉高。** 另外脚本每 3 个文件存一次盘，
中途被打断也不会丢进度。

辅助参数：
```bash

  --concurrency 6 [--path-prefix 01_活动照片] [--only <活动id...>] [--dry-run]
```
