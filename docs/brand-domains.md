# 独立品牌入口的实现与发布

一套业务代码、一份活动目录、一份数据库和一份图床。BigApple 当前部署方式为一个子域名一个应用容器，三个品牌额外运行的是同一个轻量转发程序，不运行数据库，不带 React 产物，不复制活动数据或图片。

| 品牌 | 原入口 | 独立域名 |
| --- | --- | --- |
| Polo | `/6024` | `https://polo-events.bigapple.work` |
| 有推 | `/6025` | `https://youtui-events.bigapple.work` |
| WinFlow | `/6026` | `https://winflow-events.bigapple.work` |

## 请求流程

- 品牌首页、活动详情、分类和相册路径读取主站 `/api/sites/:id/page`。它每次读取同一个已构建 HTML，仅填入当前品牌的标题与说明，标记品牌浏览模式。
- 品牌站 `/api/site` 固定转发至主站 `/api/sites/:id`，编号来自入口服务配置，不能通过路径、参数、Cookie 或请求头切换。
- 品牌站不转发管理员接口、其他品牌 API 或数字编号路径。浏览器 hash 中的管理员／编号路由也被客户端拒绝；错误页的返回链接始终指向当前域名 `/`。
- 不使用跳转到主站或 iframe。照片仍直接使用原图床，Logo 仍使用对象存储。
- HTML 和 JSON 支持 gzip，不缓存品牌配置。入口不转发用户 Cookie、Authorization 或上游重定向，主站不可用时显示错误页，不降级显示原站。
- 原站继续公开完整活动库。独立域名解决普通浏览和删除路径时的品牌归属，不把公开活动资料变成机密数据。

## 发布顺序

1. 读取线上后台当前配置并留存，确认本次更新不覆盖管理员的新选择。
2. 测试并构建主站，执行 `npm run release:prepare` 生成干净目录，再用 bigapple-deploy 更新已有 `media` 应用。原有 Secrets、持久化卷与对象存储保持。SQLite 升级至版本 2 前，启动入口会自动做一致性备份。
3. 执行 `npm run release:gateways`。查询平台注册表，复用已有 `polo-events`、`youtui-events`，创建尚未存在的 `winflow-events`。分别 `--inspect` 后按 Docker 模式部署。入口无需密码、对象存储或其他 Secret。
4. 核对每个入口 `/api/site` 的品牌、活动选择及图片，并测试根目录、详情刷新、相册和拒绝后台访问。
5. 全部验证通过后，使用已登录主站的管理员会话调用 `PUT /api/admin/resellers/:id/domain`，JSON 为 `{ "hostname": "polo-events.bigapple.work" }` 等。接口接受平台子域名，排除主站与 API 域名，并防止同一地址绑定给两家代理商。部署者必须先确认入口确实对应该编号；此接口不自动创建平台应用。
6. 验证后台“复制链接”以及旧编号路径跳转。数字编号仍作为稳定内部标识保留。

域名绑定保存于 `reseller_domains` 表。普通品牌编辑不会改变绑定，重启和重新导入也不会覆盖。新增代理商默认仍有编号链接；为其开通独立域名时，在部署映射中增加一条记录、部署入口、验证后绑定。这里尚未把平台部署权限放进业务后台，不会因点击保存就擅自创建应用。

## 后续维护与恢复

日常品牌和活动选择只在主站后台调整。只更新页面／业务逻辑时，只需部署 `media`；只有修改转发程序时才更新三个入口。所有入口共用 `gateway/server.mjs`，不会分叉维护。

各品牌入口依赖主站可用性。数据库版本 2 为域名绑定增加了表；回退到不支持版本 2 的旧主站程序前，须保留当前数据并使用升级前备份，不能只回滚容器代码。优先通过修复后重新发布恢复，避免丢失最新后台编辑。
