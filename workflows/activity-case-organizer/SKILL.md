# 活动素材整理专家

使用者是 BigApple 团队成员，多半没有技术经验，可能用 Mac 或 Windows。助手执行全部命令；对方只发素材、回答事实、看页面、说「确认」。每一步结束用一句话说清做到哪、下一步要他做什么，不让对方填 JSON、敲命令或理解哈希。`$SKILL` 指本 Skill 文件夹。

```text
开工自检 ─► 收素材、问清事实 ─► 逐张实看、按覆盖精选、作品截图 ─► 三件套本地审阅，对方确认
   ─► 团队白名单 ─► 提醒备份到团队共享硬盘 ─► 写入测试站 media-staging ─► 对方确认
   ─► 写入正式站 media.bigapple.work 并验收
```

## 先判断要做哪件事

| 对方要做的 | 读哪份 | 入口 |
| --- | --- | --- |
| 上新活动、给某场补照片或案例 | 本文 1–4 节 | `archive.py` → `publish.py` |
| 修已经上线的活动（作品视频放错、缺封面、简介太长） | [修旧活动](references/repair.md) | `repair.py` |
| 看全站还有哪些问题、修之前先摸底 | [全站体检](references/audit.md) | `audit.py` |

三条路用同一套规则 `scripts/checks.py`：上线拦什么，体检就报什么。只读当前任务需要的那份。

活动数据存在网站服务器上，每场一条原始记录，是唯一真源；打开页面时按当前皮肤渲染。GitHub 上的 media-bigapple 只是皮肤和渲染规则，图片在图床。上新、补素材、整场修改都只写这一场，不部署、不碰 GitHub；换皮肤只部署代码。

## 1. 开工自检

按顺序做完再收素材，任一项不过就停下说明原因：

1. **团队白名单**：只在上传或写站点前检查，见第 4 节第 0 步；只做本地整理和本地预览时不查。
2. **网站工程**：本机没有就 `git clone https://github.com/itooth/media-bigapple` 到对方的项目目录；有就 `git pull --ff-only`。然后 `npm ci --include=dev`。它只用来按最新规则生成这一场的数据，不存数据。pull 失败按 [release.md](references/release.md) ② 处理。下文 `/网站工程` 指这个目录。
3. **工具**：Python 3.12+ 和 Pillow、ffmpeg、Node 24+、git；有作品链接时再装 `python3 -m pip install playwright==1.64.1`，并确认本机有 Chrome 或 Edge。缺什么代为安装（Mac 用 Homebrew，Windows 用 winget），装完复查版本。

## 2. 收素材、问清事实

开场说：「先把这次活动的素材文件夹发来，照片、视频、链接混着放也可以，我先帮你盘点。」读完再向对方确认活动名称、日期、地点和案例归属。

- 网站只显示标题、日期、地点、简介、标签和素材本身，海报、logo 放进 `01_活动照片/` 就当普通照片展示。不拿示意图冒充真实素材，缺的事实（如城市）留空不编。
- 补已有活动先问清是哪场：目录名、`id` 必须和网站上那场一致，不能因为标题变了新增一场。
- 只改网站 UI 时不重新整理素材。
- 在线相册要把全部照片下载到本地，保留原文件名（含相机序号）；改了名就写 `来源元数据.json`，见 [精选方法](references/selection.md) 第 1 节。

## 3. 整理

按 [整理与数据契约](references/archive-contract.md) 做 scan → 实看填计划 → apply → 设 id 和一句话简介 → 视频封面 → mirror。作品链接、链接清单和交来的旧整理包按 [链接与输入包](references/links-and-intake.md) 处理。必须守住的规则：

- **实看再判断**：照片用 `curate.py sheets` 出编号拼图（每页 12 张，按拍摄顺序），每页看完，每张写一句自己的 `review.evidence`；认人、读桌牌或屏幕时单独打开原图。视频用 ffmpeg 抽 2–3 帧；作品链接打开看。不能凭文件名或 OCR 代替实看。字节相同的文件复用已有判断。
- **合并只限字节相同且归属相同**：同主题的图片作品、网站、视频分别保留；同名但作者、活动或成品不同的不能按标题合并。
- **看不到画面就停**：拼图或图片显示「已省略」、打不开、太糊看不清时，重新出图（缩小或分批）再看，不准凭印象、文件名或上一轮记忆命名。
- **精选按覆盖，不按张数**：目标是访客看完活动页能还原活动经过、谁做了什么、产出了什么。按 [精选方法](references/selection.md) 做：自己判断活动类型并写章节 → 逐张描述 → 连拍只指同一瞬间的重复，组内留一张，其余标 `burst-alt` 并指向留下那张 → 每个章节、每个人物或团队至少一张，没有就写原因 → `curate.py name` 自动命名。描述是唯一真源，入选照片在网站上的名称直接用它。`apply` 和 `publish.py` 会拦截缺描述、一句话套多张、缺代表照和覆盖缺口。
- **三件套交给对方审**：全量审阅页（`curate.py html`，本地直接打开）、覆盖表（`curate.py coverage`）、本地预览页，一起交。本地预览用独立后台进程启动，curl 确认能打开再发链接。对方说的保留、恢复、去掉记为 `decidedBy: user`，优先于 AI。
- **命名决定网站显示**：活动照片和视频用 `五位分数_[首页_][封面_]内容分类_描述`，分数越高越靠前，每场只能有一张 `封面`；案例目录用 `首页NN_案例名` 或 `五位分数_案例名`。人工改过的分数和标记优先。
- **视频分活动和作品，每个都要封面**：现场实拍进 `01_活动照片/`，学员做的成品进 `02_案例/<案例>/视频/`，分不清就问。跑 `video_posters.py frames` 生成封面后必须看总览图，选错就 `pick` 换。见 archive-contract.md「视频放哪」。
- **简介给人看，一句话**：manifest `summary` 不超过 20 字，案例简介不超过 15 字；长内容写「详细说明」给 Agent 读。
- **作品主图**：作品链接用 `capture_case_links.py` 多时刻取帧，选最能看出玩法或功能的一帧；只有标题、加载页或白屏的帧不能当主图。每个有截图的案例恰好一张文件名含「主图」的图。
- **归属和介绍问实习生**：哪张图属于哪个作品拿不准时必须问，不能猜；`说明.md` 的「案例简介」也向实习生要，发布前不能留空或写「待补充」。

## 4. 备份、测试站、正式站

严格按 [备份、发布与上线](references/release.md) 走，顺序不能跳：

0. **团队白名单**：`bash "$SKILL/scripts/check_team_access.sh"`（Windows 用 BigApple 自带的 Git Bash）。退出码 3 = 不在白名单：把打印的 ID 原样给对方，请他发给查理加白名单，加好后重跑。退出码 2 = 没装 APP 部署专员，引导去技能页安装。不在白名单时不要用部署专员新建同名应用或往自己的空间上传。
1. 提醒对方把整理好的活动文件夹复制到团队共享硬盘，不用问路径；对方确认后 `release_gate.py backup` 记录。没复制不往下走。
2. `publish.py --app media-staging`：传图到测试图床，只把这一场写进测试站。这就是预览，有问题改完重跑。
3. 助手先自查测试站，再发地址给对方逐项确认，然后 `release_gate.py approve`。确认后又改了素材，重走 2–3。
4. `release_gate.py check` 通过后跑 `publish.py`（不加 `--app`），传正式图床并写进正式站，线上逐项验收，告诉对方正式地址。

补照片或案例用 `--append`，只需要这批新素材；这场旧记录里的问题（简介太长、缺封面等）这时只提示不拦，助手要问对方「这次要不要顺手修」，要修就走[修旧活动](references/repair.md)。换封面、删照片、改顺序或文字要用完整目录整场更新，见 release.md「更新已有活动」。撤下活动只有查理能做。改网站 UI 才需要部署，这一步使用 bigapple-deploy Skill，见 release.md「边缘情况」。

本 Skill 不负责 commit、push、PR。上传和写入都用本机 BigApple 部署身份，不内置账号或 token。遇到不在白名单、额度不足、写入失败，停下说明卡在哪，不绕过。
