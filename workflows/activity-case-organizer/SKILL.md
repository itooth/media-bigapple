# 活动素材整理专家

一个入口贯穿归档、数据、预览和上线。使用者多半是经验不多的实习生：助手执行全部命令，对方只需要发素材、回答事实、看页面、说「确认」。沿用已有网站工程和它的媒体链路；更换版式不重新识别素材、不改活动 ID。

```text
发来素材 ─► 盘点、问清事实 ─► 实看命名分类、作品截图 ─► 本地预览、修改
   ─► 原件复制到团队共享硬盘 ─► 生成网站数据 ─► 测试站 media-staging 预览
   ─► 实习生确认 ─► 正式站 media.bigapple.work 上线并验收
```

每一步结束时用一句话告诉对方做到了哪、下一步要他做什么。不要让对方填 JSON、敲命令或理解哈希。

## 开始时

先看用户给的目录、已存 manifest/媒体映射、当前网站仓库和已确认选择。只补会影响结果的缺口；一次引导一个动作，不把内部 JSON 或技术参数交给新手填写。

首次可说：“先把这次活动的素材文件夹发来，照片、视频、链接混着放也可以，我先帮你盘点。”读完再用已有材料确认活动名称、日期、地点和案例归属。缺海报时默认用已确认封面；缺合作方 logo、PPT/PDF 时先省略对应位置，不拿示意图冒充真实素材。用户有海报/logo 就引导其发送现有文件，不要求其制作新文件。

本次只检查或改 UI 时，维持范围，不重新整理原素材。多人交接先确认同一活动 UID，不能因目录名或标题变化新增一场活动。

## 归档与持续修订

按 [整理与数据契约](references/archive-contract.md) 工作。首次用 `scripts/archive.py scan` 生成活动外计划；看图片（大图先缩到 1600px 内；批量时做带编号的拼图再逐张对号，避免顺序错位）、抽看视频（ffmpeg 抽 2-3 帧）、打开作品链接后填写分类、中文命名、判断依据和人工选择。相同内容哈希可复用视觉判断；不同案例身份仍独立。不能凭名字或 OCR 代替视觉核验。

`apply` 复制到正式目录，输入原件保留；`apply` 之后先在 manifest.json 设置 `id`（格式 `MM-DD-英文或拼音短名`，如 `10-28-yiwu-ai-class`，不能和已有活动重复，用 `git show HEAD:src/data/siteContent.snapshot.json` 查）并把 `uid` 设为活动目录名，scan 给的随机 UUID 不能用来发布；`mirror` 生成网站展示副本和两份 JSON。先保留历史记录，再更新当前索引。后续用户在正式目录改文件名、排序或素材；只重新处理内容发生变化的文件。改名优先当前目录，旧索引不能还原旧名称；内容替换必须重审。

仅合并字节相同且归属相同的媒体副本或同一案例的相同 URL；同一主题的图片作品、网站、视频分别保留。同名不同作者、不同活动或不同成品不能按标题合并。命名必须符合网站解析规则（见契约「命名」）：活动照片和视频用 `五位分数_[首页_][封面_]内容分类_描述`，分数越高越靠前，每场只能有一张 `封面`；案例目录用 `首页NN_案例名`（首页顺序）或 `五位分数_案例名`。人工改过的分数和标记优先。

链接要保存来源与归属。作品链接用 `capture_case_links.py` 多时刻取帧，实看后选最能代表玩法/功能的一帧，首屏只有标题、加载或白屏不能当主图；加载页、登录墙、失效链接保留待处理记录。链接清单与案例目录用 `match_case_links.py` 一一对应，歧义不猜。只有链接没有图的作品，先建 `02_案例/首页NN_作品名/` 再跑 match。**作品归属（哪张图属于哪个学员作品）拿不准时必须问实习生，不能猜**；作品介绍（`说明.md` 的「案例简介」）也向实习生要，发布前不能留空或「待补充」。每个有截图的案例必须恰好一张文件名含「主图」的图（只有一张图时可省），网站每个案例只展示主图。交来的旧整理包、压缩包先用 `absorb_input_packages.py` 比对吸收，已覆盖的重复媒体不再保留。细则和命令见 [链接与输入包](references/links-and-intake.md)。

同一活动分批补素材，或复用以前活动里同一批照片时，`scan` 加 `--archive <已整理活动目录>`：字节相同且只有一个去向的文件直接继承已审核的分类、命名、角色和选中状态，记入 `inheritedFrom`；多个去向列进 `candidates` 待定。`apply` 合并到 `其他/整理记录.json`，保留各批次记录。只改名不会重新压缩。截图进对应案例，原始链接文件保留。源码及内部附件归档，但不自动公开下载。

## 本地预览

按 [执行命令](references/commands.md) 用 `catalog.py` 生成本地预览，在网站工程里构建并打开给对方看，确认封面、照片选择与顺序、案例对应和文案。这一步用于快速修改；最终以测试站为准。统一详情版式：左标题简介、右海报/封面；「图片视频」「案例」两个主分区；资料折叠区；一行「下载全部素材」。需要改 UI 时改仓库的 EventDetail/CSS，不改归档协议。缺城市等事实保持空值，不编造。

## 备份、上线与验收

严格按 [备份、发布与上线](references/release.md) 走，顺序不能跳：

1. 原件复制到团队共享硬盘，问清目录，`release_gate.py backup` 记录。没复制不往下走。
2. `publish.py` 上传展示图、增量写入网站数据、构建、测试；其他活动保留。
3. 推到 `activity/<id>` 分支，用「APP 部署专员」部署测试站 `media-staging`，助手先自查。
4. 把测试站地址发给实习生，逐项确认后 `release_gate.py approve`。确认之后又改了素材，就重新走 2–4。
5. `release_gate.py check` 通过 → PR 检查通过再合并 → 用 APP 部署专员更新正式应用 `media` → 线上逐项验收 → 告诉对方正式地址。

部署只用 APP 部署专员（bigapple-deploy），先读其当前文档；不要内置账号、token 或另建正式站。遇到额度不足、权限不足、合并冲突，停下说明卡在哪，不绕过。
